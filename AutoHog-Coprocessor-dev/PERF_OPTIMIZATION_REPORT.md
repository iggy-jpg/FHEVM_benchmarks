## 0. 2026-07-27 OOM 与密文确定性审计

### 0.1 OOM 结论与修复

失败基准 `parallel_arith_random_r100_omp48_20260726_214011` 的退出码为 137。
用户 cgroup 的 `memory.events` 记录 `oom_kill=1`，`memory.peak` 为
`519054835712` byte（约 519.1 GB），因此这是系统 OOM kill，不是算术错误。
4--128 位均完成 ADD/GT/MUL/DIV 各 100/100；256 位完成前 80 组，第 81 组在 DIV
期间被杀。被记录的所有结果均解密正确。OOM 前第 81 组 MUL 从约 37--39 秒恶化到
664 秒，说明系统已处于严重内存压力。

根因及修复如下：

1. spqlios 的线程局部 `FFT_Processor_Spqlios` 析构只删除表包装对象，未释放 FFT/IFFT
   表内部的 `malloc` 缓冲区，同时遗漏 `reva`。现在 FFT/IFFT 表具有匹配的销毁接口，
   并完整释放表缓冲、表对象、`reva` 和余弦表。
2. DIV 的宽减法曾按 block 数创建 OpenMP 线程，256 位可请求 86 线程，绕过顶层的
   48 线程要求。现在 `threads_hint` 从 DIV/MUL 传递至加减法、批量 PBS 和并行循环，
   并同时受 `OMP_NUM_THREADS` 与 `OMP_THREAD_LIMIT` 限制。
3. 基准按位宽启动冷进程，逐算子记录结束时间、正确性、当前/峰值 RSS 和进程线程数；
   `/usr/bin/time -v` 另记录每个位宽进程的用户/系统 CPU 时间、峰值 RSS 和退出状态。

spqlios 回归测试反复创建并销毁 48 个工作线程 40 轮；服务器最终复测结果为：基线
9104 KiB、峰值 10344 KiB、结束 9440 KiB，净增长 336 KiB，未再出现按轮次线性增长。
隔离的 256 位 DIV 压力测试连续执行 3 次，均解密正确且实际线程数为 48；三次结束时
RSS 分别为 281216、298996、299044 KiB，进程峰值 345644 KiB，退出码为 0。第二次到
第三次仅增加 48 KiB，表明分配器预热后 RSS 已稳定，而不是随样例数持续线性增长。

### 0.2 四个算子的实际执行逻辑

- **ADD**：`HomAdd_pal` 在 48 线程下选择宽并行路径；每个 3-bit block 生成
  `(G,GP)`，通过 radix-3 Brent--Kung 前缀网络传播 carry，最后由 FA3 PBS 提取和。
- **GT**：接口为有符号比较。双方 MSB 先通过免费线性取反把二补数顺序映射为无符号
  顺序，再由 GT3 叶节点和三态 `(G,GP)` 归约树计算结果。
- **MUL**：无符号 `W x W -> 2W` 完整乘积。真实 `W x W` 区域生成 2x2 部分积，
  使用最多 15 输入的 popcount PBS 压缩各列，最后执行宽 carry adder。
- **DIV**：无符号窗口化恢复除法。先计算除数 suffix-OR，每轮执行有效窗口减法、商位
  PBS 和余数 Select；返回 W-bit 商和 W-bit 余数，除零语义为 `q=0,r=A`。

每个随机样例按 ADD、GT、MUL、DIV 顺序执行，只有单个算子内部使用 48 线程；加密、
解密和明文参考校验不计入算子计时。

### 0.3 密文确定性边界

确定性工具将秘密密钥、**系数域** bootstrapping key、IKS key、常量密文和输入密文保存
为同一份 portable-binary 工件（SHA-256：
`a4a6f2d2a179d37c599e8b55be7597e311edd071a90072f32e75ac62bae7c10b`）。评估节点加载
同一工件后才各自转换 FFT 表示，因此比较没有混入重新加密或重新生成密钥的随机性。

| 场景 | 解密语义 | 原始输出密文 | 结论 |
|---|---|---|---|
| 同一私钥下独立加密 | 相同 | 不同，4 位输入的 8196 个系数均不同 | 私钥相同不足以逐字节一致 |
| x86 spqlios、48 线程、同拓扑重复两次 | 相同 | 完全一致，输出 SHA-256 均为 `973c5958e70086cf5e0199ce9d0335969d8d77f10d98abba082eceeafe53fb52` | 当前构建内可复现 |
| x86 spqlios、1 线程与 48 线程 | 相同 | 24588 个系数不同 | `_pal` 随线程数选择了不同电路拓扑 |
| x86 spqlios 与 Apple arm64 FFTW、均 1 线程 | 相同 | 43029 个系数不同 | 跨机器、跨 FFT 后端不位精确 |

跨后端差异覆盖 ADD、GT、MUL、DIV 的全部输出密文，清低 4 位后仍有 43029 个差异，
最高差异位达到 bit 63。清低位仅是诊断，不能作为原始密文一致的通过条件。因此当前
系统满足解密语义一致，但**不满足跨 FFT 后端逐系数共识**。需要逐系数共识的节点必须
固定同一后端、构建、线程预算及由此确定的算术拓扑，并仍应通过部署前对拍确认。

这里必须区分四件事：批量 IKS 与逐个 IKS 位精确，只证明 IKS 实现；同后端同拓扑重复
可复现，只证明该固定执行配置；完整 PBS 的跨后端一致性本次明确失败；解密结果一致也
不能推出密文字节一致。

## 2. 成本模型（所有优化的依据）

本库是位级 TFHE：每个明文比特是一个 `TLWE<lvl2param>`（n=2048, k=1, l=2, T=uint64, μ=2^58）。

**一次 PBS = 1 次 IdentityKeySwitch + 1 次 BlindRotate + 每输出一次多项式乘。**
实测占比：**BlindRotate 86%（~32 ms）、IKS 7%（~2.5 ms，批量后 0.6 ms）、
每额外输出 ~0.5%**。由此得到三条优化原则：

1. **减少 PBS 次数** —— 决定串行时间与总吞吐。
2. **减少关键路径层数** —— 决定多核墙钟时间。二者常需权衡（见 §3.7 的两档接口）。
3. **多输出几乎免费** —— 一次 PBS 可输出多行 LUT，是本项目最大的杠杆来源。

**LUT 门编码**：`Linear(weights, t_size)` 把加权和作为 LUT 索引，LUT 只做位提取。
约束（与既有已验证门一致）：`Σwᵢ·mᵢ ≤ t_size−1`（防负循环回绕）、`Σw² ≤ 85`、
`t_size ≤ 16`。

**关键洞见**：`Linear` 的输入可以是**算术加权和**，而非仅布尔组合。这是列 popcount
压缩（15:4/次）、比较器 3 位叶、三态前缀网络的共同基础。

## 3. 已实施的优化

### 3.1 明文常量算子族（`src/HomPlainOps.cpp`，业务热路径）

**乘法**：`k` 为明文时，部分积 `Σ_{kᵢ=1}(A << i)` 的每一行都是密文位的**移位复制
（零 PBS）**，无需任何 AND 门；成本只剩列压缩 + 末级进位加法。

**除法**（Granlund–Montgomery 魔数法）：明文侧取 `L = ⌈log₂d⌉`、`m = ⌈2^(W+L)/d⌉`，
则对所有 `0 ≤ A < 2^W` **精确成立** `⌊A/d⌋ = (A·m) >> (W+L)`。
> 证明：令 `e = m·d − 2^(W+L) ∈ [1, d−1]`（d 非 2 的幂），`A = qd + r`，则
> `A·m/2^(W+L) = q + r/d + A·e/(d·2^(W+L))`，扰动 `< 2^{−L} < 1/d`，
> 故 `r/d + 扰动 < (d−1)/d + 1/d = 1`，取整不变。∎

密文侧只需**一次明文乘法 + 免费移位**得商；余数 `r = A − q·d` 再花一次低半明文乘 +
一次减法。特例全免费：`d=0`（q=0, r=A）、`d=1`、`d` 为 2 的幂（纯移位）。
**魔数乘积不可截断低列**——原因见 §7。

**CSD/NAF 重编码**：常量按 二进制 / CSD 中非零位更少者展开（128 位随机常量平均
63.9 → 43.2 非零位）；负数行 = 免费线性取反 + 补码常量归并。经 W=1..8 全输入穷举验证。

**定宽变体**：标准位宽（64/128）的定宽语义只需 `A·k mod 2^W`。定宽版仅生成/压缩低 W 列
（部分积为三角形而非平行四边形，末级加法也减半宽），**比全宽版快 2.2-2.4×**。

**只出商变体**：余数占全流程约 1/3（并行下更高，因其并行度低于魔数乘的大波次）。
实测 W=128 并行 13.3 s → **9.49 s（−36%）**，W=64 6.63 → **3.67 s（−45%）**。

**共用常量的批量接口**：N 路共用同一常量的操作相互独立，按**"实例级并行 × 实例内
串行"**调度（N ≥ 线程数时）——每实例走串行引擎（PBS 总数的下确界），N 个实例填满
全部核心。实测 N=20/W=16：批量 6.77 s vs 逐个并行调用 14.87 s = **2.2× 吞吐**
（核数越多差距越大）。N < 线程数时自动回退逐实例并行。

**其他明文操作数算子**：

| 算子 | 成本 | 对比密文版 |
|---|---|---|
| `HomANDPlain` / `ORPlain` / `XORPlain` | **0 PBS**（复制 / 线性取反 / 常量） | 原 ⌈W/2⌉ 次 |
| `HomSelectPlain`（两明文分支按密文位选） | **0 PBS** | 原 W 次 |
| `HomEQPlain` | ~W/14 次（逐位匹配免费，只付 AND 树） | 原 ~⌈W/2⌉+树，**~5×** |
| `HomGT/GE/LT/LEPlain` | 4 位/叶 + 三态归约树，W=128 约 49 次 | 原 85 次，**省 ~42%**；四算子共享一棵树 |

> 明文**加/减数**没有算法优势（进位仍依赖密文位），用平凡加密 + 现有 `HomAdd` 即可。

### 3.2 乘法（`src/HomMul.cpp`）

原实现：逐对 AND（2 积/PBS，且对零扩展位白算近一半）+ 3:2 压缩器（每 PBS 仅消 1 比特）。

1. **2×2 瓦片部分积**：`Mul2x2_PBS` 一次 PBS 输出 2 位×2 位乘积的 4 个基本积，且只
   枚举真实 W×W 区域 → 部分积 PBS 数降至 1/4。
2. **列 popcount 压缩**：等权重加权和即列内比特计数，一次 PBS 最多 **15:4**
   （Σw²=15，远低于包络），压缩层数从 ~20+ 降到 3-5。
3. **尾部整层冲刷**：列高全 ≤3 时一轮收敛，消除大位宽下的进位涟漪。
4. **末级进位加法上下文感知**：嵌入乘法内的 CPA 是延迟关键路径，其盈亏平衡点是
   ~4 线程（而非 §3.7 的吞吐阈值），≥4 线程即走宽前缀版。

PBS 数（W=128 全乘积）：**~49,000 → ~5,600**。另导出 `HomMulRectWindow`（矩形操作数
+ 列窗口）与 `HomColumnsCompressAdd`（列压缩引擎），供除法与明文算子复用。

### 3.3 除法（`src/HomDiv.cpp`、`src/HomDivNewton.cpp`）

**窗口化恢复余数除法**（默认）：

1. **窗口化**：第 i 轮余数只有 i+1 个有效位，比较与更新只做窗口宽度 → 工作量减半；
2. **B 的后缀 OR 预计算**（2 输出/PBS 链）：窗口外比较归结为单一信号，并直接取代
   末尾整条 `HomEQ` 除零检测；
3. **商位融合门**：一次 PBS 同时输出真实比较 `ge` 与已折入除零保护的商位——
   **删除了原来两次全宽终选**（B=0 时余数结构上自动保持为 A）；
4. 串行版用**掩码减法**（3 位/PBS）替代逐位 Select；并行版保留深度 1 的 Select。

语义完全不变（含除零 q=0, r=A）。PBS 数（W=128）：**~22,000 → ~8,400**。

**Newton 迭代除法**（`HomDivNewton`，备选）：倒数 Newton 迭代（4 位种子 LUT →
精度倍增 21→37→69→131 位）+ **精确 ±B 校正**（证明 |Q̂−Q|≤3，实测最多 1 步），
输出是**精确整数商/余数，非近似**。
> **48-128 核不要启用**：总工作量约 4×，深度优势要数百核才兑现。保留作为
> GPU / 数百核选项。

### 3.4 加 / 减法（`src/HomAdd.cpp`、`src/HomAdd_unsigned.cpp`）

1. **CarryCombine 整层删除**：进位 `G|(P&C₀)` 中 `C₀` 恒为编译期常量（加 0 / 减 1），
   而 `GP = G|P` 可作为前缀节点的**免费第三 LUT 行**输出，于是
   `Cin[i+1] = carry_in ? GP : G` 零 PBS 完成 → 省 ⌈W/3⌉ 次 PBS + 1 层深度。
2. **Brent-Kung 基数 3 前缀网络**替换 Kogge-Stone 基数 2：利用 (G,GP) 三态编码
   （kill/propagate/generate），一次 PBS 合并 3 段（权重 {4,4,2,2,1,1}，t15，Σw²=42）。
   前缀 PBS 数（W=128，43 块）：**195 → 60，深度不变**；噪声也更低（42/t15 与 10/t7，
   低于原 85/t16）。

### 3.5 比较与相等（`src/HomComp_unsigned.cpp`、`src/HomComp.cpp`、`src/HomEQ.cpp`）

1. **GT3 三位叶**：`v = A₃ + ~B₃`（取反线性免费），`E=[v==7]`、`G=[v≥8]`（Σw²=42/t15）
   → 叶子数从 ⌈W/2⌉ 降到 ⌈W/3⌉。
2. **三态归约树**：叶子改输出 (G, GP)（免费行），二叉 EGcombine（Σw²=85）替换为
   三态 C2/C3 归约 → 合并节点数减半，深度 −2，噪声更低。W=128 无符号比较
   **127 → ~65 次 PBS**。
3. **有符号比较归约到无符号**：二补数序 = 双方符号位取反后的无符号序（取反免费）。
   `HomComp.cpp` 全部 8 个入口成为薄封装，有符号比较 PBS 数减半。
4. **EQ3 三位叶**：`v == 7` 判定（Σw²=42/t15），叶子 ⌈W/2⌉ → ⌈W/3⌉，AND16 树同步缩小。

### 3.6 PBS 层（`include/HomGate.h`）

1. **稀疏精确 PolyMul**：`PBS_Multi` 逐输出原走整数 NTT 路径（207 μs/输出，且
   Goldilocks 域往返带 ±5 LSB 舍入）。改为 ≤16 抽头的负循环移位-累加：
   **位精确、~15 μs**；且 `SampleExtract` 只读 b 行第 0 系数，故 b 行整条乘积退化为
   16 次标量累加。4 输出门每次 PBS 省 ~0.7 ms。
2. **批量密钥切换**：`PBS_Multi` 拆为 KS + `PBS_Multi_body`；新增 `BatchKeySwitch20`
   （`CatIdentityKeySwitch` 分块，**自适应块宽 16/8/4/2** 贪心切分——固定 16 会让
   任务数 <16 的波次整体退回标量路径）与 `PBS_Multi_batch`（批量 KS + 并行盲旋转）。
   实测每输入：标量 2.48 ms → **0.60 ms（T=1）/ 0.375 ms（T=8）**，即 **4.1× / 6.6×**。
   结果与逐个 IKS **位精确一致**（0 字差异）。该结论只覆盖 IKS，不能外推到完整
   PBS、不同算术拓扑或不同 FFT 后端；完整边界见 §0.3。
   已接入全部独立波次：乘法瓦片/压缩、Select、加法器 pgblock+FA3、比较器叶与树、
   EQ 叶与 AND 树、除法 MaskNot 波次、明文比较树。
3. `PBS_Single` 每次调用 32 KB 死写删除；CAT 暂存改 `thread_local`（原 300 KB 在栈上，
   高线程数有溢出风险且每块重复清零）；批量按区间分片，中间态内存有上限。

### 3.7 两档接口与选型阈值（`include/HomUtil.h`）

深度优化型并行（前缀加法器、比较树）总 PBS 数多于串行链，只有线程数超过盈亏平衡点
才回本。因此：

- **`xxx_pal`（默认）**：按线程数**自动选型**——低核走最少工作量路径，高核走深度
  优化路径。
- **`xxx_wide`（显式）**：无条件走深度优化路径，供高核部署或 A/B 对测。
- `AUTOHOG_WIDE_THRESHOLD` 可全局覆盖（设 1 强制 wide，设大值强制串行）。

阈值经冷进程实测校准（W=128 加法）：T=2 串行胜；**T=4 wide 胜 1.31×**；T=6 1.40×；
T=10 1.54× → 加法/减法平衡点 ~3，比较器 ~2（其 wide 版只多 ~50% PBS，而加法器多 3.4×）。
**默认 4，比较类传 2。** 无工作量-深度权衡的算子（Select、EQ、乘法压缩、批量接口）
不受影响，任何核数直接受益。

### 3.8 协议驱动层的明文常量折叠（`check_select.cpp`、`test_consensus.cpp`）

协议本就能表达明文操作数（op 16 常量装载、`is_scalar==1` 字面量），但此前它们被平凡
加密后走全密文算子。现在驱动维护 handle→常量值 注册表，派发时自动路由：

| op | 折叠条件 | 路由 | 收益 |
|---|---|---|---|
| 5 AND / 6 OR | 任一操作数为已知常量 | `and/or_plain` | **零 PBS** |
| 11 GE / 14 LT | 任一操作数为已知常量 | `ge/lt/le/gt_plain`（有符号版自动匹配） | 省 ~40-60% |
| 15 Select | 两个数据分支均为常量 | `select_plain` | **零 PBS** |

协议文件与结果语义零改动；`AUTOHOG_DISABLE_PLAIN_FOLD` 为逃生阀。
**A/B 等价验证**：真实协议流水线（28 算子、W=256）折叠开/关解密结果逐行一致。
该测试流水线以加/减/双密文 select 为主，驱动级提速 ~8%；收益取决于业务 op 构成。

## 4. 缺陷修复

### 4.1 库正确性与构建缺陷（影响所有平台）

| # | 严重度 | 缺陷 | 修复 |
|---|---|---|---|
| 1 | **高** | `HomSub_unsigned(_pal)` 在 `W%3==0`（无补位路径）时 `ovf_ct` 返回**进位而非借位**（二者互为取反）。原测试只覆盖 W=4/8/16/32 故从未触发 | `src/HomAdd_unsigned.cpp`：pad==0 时对进位做线性取反。对所有调用方均为纯正确性改进 |
| 2 | **高** | `homops` 含 `ZKProof.cpp`（用 OpenSSL EVP/SHAKE256）却不链接 OpenSSL；各测试程序靠自己补链掩盖，但**只链 `homops` 的 `fhe-api` 共享库因此无法构建**（对外 FFI 库在仓库原状态下链接失败） | `CMakeLists.txt`：`find_package(OpenSSL)` 前置，`homops` 以 **PUBLIC** 链接 OpenSSL，全部消费者自动继承 |
| 3 | **高** | `check_select.cpp` 协议 op-15 的 select **分支反向**，与 `test_consensus.cpp` 对同一协议输入返回相反分支；其 sanity check 的期望值也错 | 对齐库约定 `sel ? B : A`，并修正 sanity check |
| 4 | 中 | `FheKey::decryptBatch` 对 W 非 8 倍数**堆越界读**（所有 1 位比较结果都会踩；每元素 16 KB，通常静默出错而非崩溃） | `include/fhe_key.h`：尾字节按实际位数读取 |
| 5 | 中 | 无符号加/减 4 个入口、`HomEQ(_pal)`、`HomAND/OR/XOR`、`HomSelect` **缺输入尺寸校验**（有符号版有），宽度不匹配时静默越界 | 全部补齐 |
| 6 | 中 | 串行压缩尾部的涟漪策略在宽输出（outW>96）下轮数 ~outW 且总 PBS 反超整层冲刷，叠加固定 64 轮的收敛守卫 → W=128 批量卡死 37 分钟后抛异常 | 串行也改用整层冲刷；守卫改为按初始比特数的动态上界 |
| 7 | 低 | `HomEQPlain` 的 AND 树对单元素组仍做一次 PBS | 直接透传 |
| 8 | 隐患 | 整数 NTT `PolyMul` 对 torus×torus 输入会**静默算出完全错误的结果**（现有调用恰好都合法） | 已由 §3.6-1 从 PBS 热路径移除；记录在案 |

**另有一项由本次优化自身引入并已修正**：两档选型阈值最初被设为 24，源于一批**受热
节流污染**的基准数据（连跑时后续算子耗时被夸大最多 5×）。改用冷进程逐算子测量后
重新校准为 4 / 2，使 10 核默认路径的加/减/比较提速 1.5-2.3×。教训见 §8。

### 4.2 macOS 开发环境适配（全部有 `APPLE AND arm64` 条件保护，不影响 x86）

- `loadAnnihilateKey` 在子线程栈上放数 MB 临时对象 → macOS 512 KB 子线程栈必然溢出崩溃
  （Linux 8 MB 栈掩盖了它）；改为堆分配。
- FFTW processor 线程安全化（`thread_local` + planner 互斥、移除析构中的 `fftw_cleanup`）——
  原实现的数据竞争会让所有 `_pal` 结果出错。
- 静态初始化顺序段错误：移除无人引用的全局 `trgswonelvl1/2`（它们在 FFT 后端就绪前
  执行 FFT）。
- `make_unique_for_overwrite` 按编译器能力条件化（Apple clang 13 的 libc++ 缺该特性）。
- `-mcpu=native`（AppleClang arm64 不接受 `-march=native`）、OpenMP 接入、Homebrew 路径。
- **`TFHEpp_DEFINITIONS` 传递** —— 此项对所有平台必要：消费者不应用这些定义会选错
  FFT 后端而链接失败。

## 5. 安全性说明

- **未改动**任何 TFHE 参数、密钥结构、密文维度、噪声参数 α、或 PBS 机制。
- 所有新增 LUT 门逐一核验：最大加权和 ≤ t_size−1（无负循环回绕）、Σw² ≤ 85
  （既有 `PGcombine_PBS` 的已验证包络）。最重的新门 Σw²=85 与之同档；多数新门
  （popcount Σw²≤15、三态 C2/C3 为 10/42）**噪声低于**原有门。
- 每次 PBS 重置噪声，故位宽加深不影响单门噪声预算；优化后总 PBS 数减少，
  整体解密失败概率**下降**。
- 控制流只依赖公开量（位宽、常量），从不依赖密文数据。
- **批量密钥切换与逐个 IKS 位精确一致**（0 字差异，单线程与多线程均验证）。这不代表
  完整 PBS 跨后端位精确；部署确定性限制见 §0.3。

## 7. 未实施的优化及理由

### 7.1 有收益但需目标机验证后决定

| 优化 | 预期收益 | 未做的理由 |
|---|---|---|
| **基数-4 SRT 密文除法** | W=128 在 **T≥48 时 1.96×**（深度 1297→663，PBS 增至 1.5×） | 10-24 核仅 1.1×，本机无法验证收益；且业务除数为明文时用不到密文除法 |
| **跨实例批量阶段融合** | T=48/N=4 模型 **2.76×**（N < 线程数时填满波次并合并 CPA 尾巴） | 收益全在高核；本机 10 核只有 1.3-1.5× |
| **CatIKS 覆盖再扩展 / KS-r3 前缀** | 单次加法延迟：深度 6→4 | 工作量 2.2×，仅当核 ≥64 且延迟压倒吞吐时才值得 |
| **Karatsuba 密文乘** | 15-25% | 明文常量场景下密文乘非热路径，优先级低 |

### 7.2 需业务条件才有意义

| 优化 | 触发条件 |
|---|---|
| Barrett / 预计算倒数（密文分母复用） | 业务中出现"同一**密文**除数被反复使用"的模式 |
| GPU / 数百核后端 | 平台工程；也是 Newton 除法唯一能翻盘的场景 |

### 7.3 已量化但收益/复杂度不划算

**跨列加权压缩器**：`Linear` 支持加权输入，故一次 PBS 可同时吃多列（列 c 权 1、
c+1 权 2、c+2 权 4，加权和 ≤15），使尾部（列高 3-4，单列每 PBS 仅净减 1 比特）
效率提升 3-4×，整体 PBS 省 17-39%。**但其输出落进邻列造成涟漪，并行波次会暴涨**
（W=128 定宽 4→44 波），只对串行路径（含批量接口的实例内串行）是纯收益。
经评估收益/复杂度比不划算，暂不实施。

### 7.4 已验证不可行（勿重试）

| 想法 | 否决依据 |
|---|---|
| 魔数乘法只算高半部（截断低列） | 正确性余量由 `e = m·d − 2^K ∈ [1,d−1]` 决定，是 O(d) 常数级；而丢列会同时丢掉**向上传播的进位**，损失随 2^T 增长（实测 W=12/d=3/保护 4 位：损失 1026 vs 余量 2）。**加大魔数精度也买不到余量**（e 恒在 [1,d−1]）。硬件 `mulhi` 之所以可行，是因为它仍形成**完整**乘积、只在最后丢弃低半字 |
| `Linear()` 零初始化与首项赋值融合 | 实测**负收益**（11.68 → 12.76 μs）：clang 对零填充 + 统一 `+=` 的向量化更好 |
| 融合溢出门（`Overflow_PBS` 并入 MSB 块） | 设计可行（省 1 PBS + 1 层），但 `compute_overflow` 在封装层默认关闭、协议驱动从不使用，实际收益为零 |
| 压缩列索引化（消除 TLWE 拷贝） | W=128 明文乘的 340 MB 拷贝仅占墙钟 **0.3%** |

### 7.5 待业务决策

- **协议层乘法语义**：`fhe_key.h::mul` 仍返回 2W 全宽（保持兼容）。若协议为定宽语义，
  应切到 `mul_low` / `mul_plain_low`，可省一半成本。
- **`sanitize_tlwe` 策略**：README 的共识清单要求每次 PBS 后清低 4 位，但乘/除法与
  新增算子未做（与原实现一致）。这是共识确定性策略问题而非性能问题，需决定是否全面启用。

## 8. 测试与验证方法

### 8.1 正确性

- **门级穷举模拟**：每个算子按 LUT 索引逐门转写为明文网表模拟（非算术近似），
  小位宽穷举（加/减/比较/乘/除 W≤8 全输入对）+ 大位宽随机与毒例；每次 `Linear`
  调用插桩断言包络约束 —— 零违例。
- **黄金模型**：Newton 除法先建位精确 Python 模型（W=1..10 穷举 130 万例 + W=128
  12 万针对性用例），C++ 逐比特镜像后三方对拍（镜像 == 模型 == 明文除法）。
- **FHE 实测**：`test_MULDIV`（W=3..128）、`test_NDIV`、`test_ADD_unsigned`（pad=0/1/2）、
  `test_ADDSUB_signed`、`test_GT_unsigned`（尾叶 1/2/3 位）、`test_COMP_signed`
  （INT_MIN/−1、MAX/MIN、相等）、`test_EQ_ops`、`test_PLAIN_OPS`（含字节序对拍与
  毒例常量）、`test_CAST` —— 全部通过，串行/并行/明文三方一致。
- **对抗性审查**：多轮独立审查（正确性反驳、噪声包络、边界猎手）。缺陷 #1 由实测
  失败推演与独立模拟审查双向确认。

### 8.2 性能测量方法（重要）

**基准必须逐算子冷进程运行。** 本机连跑多个算子时热节流会把后续算子耗时夸大最多
**~5×**，据此做出的设计决策会长期悄悄拖慢默认路径 —— 本项目的选型阈值就曾因此被
设错（§4.1 末）。任何"并行反而更慢"的结论都要先排除节流。

```bash
# 全算子（34 个）并行基准，逐算子冷进程 + 冷却间隔，结果存入 results/
./run_perf_all.sh "64 128" 2 8

# 只跑关心的算子
AUTOHOG_PERF_OPS="add_u sub_u select mul_plain_low div_plain_q" ./run_perf_all.sh "64 128" 2 8

# 指定线程数
OMP_NUM_THREADS=48 ./run_perf_all.sh "64 128" 2 8
```

`test_PERF_ALL` 覆盖 34 个算子（密文加减乘除、全部比较、位运算、Select、CAST、
明文乘除与比较、零 PBS 算子），每项自带正确性校验，支持单算子过滤与 `list`。

## 9. 部署指引（x86，48-128 核）

### 9.1 构建

x86 **不设任何 FFT 后端选项即自动使用 spqlios**（TFHEpp 的 `else()` 默认分支）：

```bash
cmake -S . -B build          # 不要设 -DUSE_FFTW3=ON
cmake --build build -j
# 确认：以下应全为 OFF，且 libspqlios.a 存在
grep -E "^USE_(FFTW3|MKL|SPQLIOX_AARCH64|CONCRETE_FFT):" build/CMakeCache.txt
ls build/thirdparties/TFHEpp/thirdparties/spqlios/libspqlios.a
```

**后端必须统一**：本次复用同一系数域评估密钥和输入密文的跨机测试表明，FFTW 与
spqlios 的完整算子输出不逐系数一致，且差异并非清低 4 位即可消除。FFTW 同一构建、
同一 1 线程拓扑重复两次可以位精确复现，但这不能外推到跨后端场景。历史性能数据主要
来自 FFTW；x86 生产部署使用 spqlios 时应单独测量，不能通过固定换算系数替代实测。

### 9.2 服务器选型

**① CPU 的 L3 容量 —— 本负载最被低估的指标**

每次 PBS 流读 **自举密钥 89 MiB + 切换密钥 117 MiB**，两者**只读且线程间共享**。
能否驻留末级缓存，决定 48+ 线程时是否撞上 DRAM 带宽墙：

| 平台 | 末级缓存 | 后果 |
|---|---|---|
| 开发机 M1 Pro | 24 MB | 每次 PBS 都从 DRAM 流（本报告带宽预警的根源） |
| **AMD EPYC 9004** | **最高 384 MB** | 89 MB 自举密钥可基本驻留 → 直接消除该瓶颈 |
| Intel Xeon 4/5 代 | 百 MB 级 | 部分驻留 |

**同等核数下优先选 L3 大的型号。** 该项在 48-128 核区间的贡献可能超过指令集差异。

**② 内存子系统**

- **带宽**：若 L3 装不下密钥，48 线程约需 130 GB/s、128 线程约 350 GB/s
  （每线程 ~2.8 GB/s）。8 通道 DDR5 单路有效带宽 ~200-300 GB/s → 128 线程单进程会饱和。
- **NUMA**：双路机**建议每 socket 一个进程分片任务**，各持一份 EvalKey 副本
  （206 MB/socket，换来本地访问）；退而求其次 `numactl --interleave=all`。
- **容量**：`N并发 × 每算子工作集 + 206 MB 密钥`。工作集主要是列上的 TLWE（每个 16 KB）：
  W=128 明文乘约 130 MB。例：每 socket 48 路并发 ≈ 6.5 GB，双路留 32-64 GB 稳妥。

**③ FFT 后端与指令集（估算项）**

spqlios 是为 TFHE 负循环 FFT 手写的 AVX2/FMA 汇编（twist 乘法融入变换内部）；
FFTW 是通用库（twist 为独立两趟 + 运行期 codelet 调度）。本机折算：每个 1024 点复数
FFT 约 **7.5 μs ≈ 6.8 GFLOP/s**，仅为 M1 P 核双精度峰值的 **~14%** —— 这个余量正是
专用核能吃掉的部分，据此**估算 1.5-3×（非实测）**。

注意这**主要是"专用核 vs 通用库"的差距，不是 x86 对 ARM 的优势**：TFHEpp 自带
ARM 原生的 `spqliox_aarch64`（需 xbyak_aarch64），在 ARM 上同样能拿到大部分收益。

**④ 其他**

只用物理核（FFT 为 FPU 密集，SMT 无收益）；显式传 `threads_hint = 物理核数`
（默认只取硬件并发的一半）；`OMP_PROC_BIND=close`、`OMP_PLACES=cores`。

### 9.3 算子选型

| 场景 | 用 |
|---|---|
| 定宽语义的乘法 | `HomMulPlainLow*` / `FheKey::mul_plain_low`（比全宽省一半） |
| 只需商的除法 | `HomDivPlainQuotient*`；`FheKey::div_plain` 已自动走此路径 |
| 商与余数都要 | `HomDivPlain*` / `FheKey::divmod_plain` |
| 共用常量的多路操作 | `HomMulPlainLowBatch` / `HomDivPlainQuotientBatch`，**攒批到 ≥ 核数再下发** |
| 密文除法 | `HomDiv_pal`（**勿用** `HomDivNewton`，数百核以下更慢） |
| 两档阈值 | 默认值（4 / 比较类 2）在 48-128 核上一律走 `_wide`，无需调整 |

### 9.4 上线前的目标机验证

跑两遍不同线程数，即可把**核数因素**与**单次 PBS 速度因素**分离：

```bash
OMP_NUM_THREADS=10 ./run_perf_all.sh "64 128" 2 8   # 与本报告 10 核数据同条件对比
OMP_NUM_THREADS=48 ./run_perf_all.sh "64 128" 2 8   # 目标配置
```

同时建议复核：(1) `AUTOHOG_WIDE_THRESHOLD` 默认值是否仍最优（机器的 PBS 速度与
并行效率变了，平衡点可能微移，用该环境变量 A/B）；(2) 并行扩展的转折点在多少线程 ——
据此决定"单进程多线程"与"多进程分片"的配比。
